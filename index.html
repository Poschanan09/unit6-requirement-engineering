วิศวกรรมความต้องการ (Requirements Engineering - RE) คืออะไร?

กระบวนการที่เป็นระบบ (Systematic Process) ในการค้นหา (Discover), สกัด (Elicit), วิเคราะห์ (Analyze), จัดทำข้อกำหนด (Specify), ตรวจทาน (Validate) และบริหารจัดการ (Manage) บริการต่างๆ ที่ระบบจำเป็นต้องส่งมอบ พร้อมทั้งเงื่อนไขและข้อจำกัดในการดำเนินงาน เพื่อเป็นพิมพ์เขียวเดียวที่แปลงความต้องการทางธุรกิจของมนุษย์ให้กลายเป็นแบบแปลนซอฟต์แวร์ที่พัฒนาและตรวจรับได้จริง

ในโมเดล SDLC แบบดั้งเดิม (Waterfall) และแบบ Agile (Iterative), RE ทำหน้าที่เป็น "สะพานเชื่อม" ระหว่างปัญหาทางธุรกิจสู่การสร้างระบบ:

คุ้มค่าด้านงบประมาณ, เทคโนโลยี, และเวลาหรือไม่
03
ความต้องการของซอฟต์แวร์ (Requirement Engineering) ★

ลำดับชั้น 3 ระดับของความต้องการ (Hierarchy of Requirements)

ตามหลักสากล (BABOK & Sommerville) ความต้องการถูกแบ่งออกเป็น 3 ระดับ เพื่อสื่อสารกับผู้มีส่วนได้ส่วนเสียที่ต่างกัน:

1. ความต้องการทางธุรกิจ (Business Requirements) ระดับผู้บริหาร / องค์กร

เป้าหมายระดับสูงขององค์กร เหตุผลทางธุรกิจที่ต้องสร้างระบบ เช่น "ต้องการลดต้นทุนการประมวลผลเอกสารลง 40% ภายใน 1 ปี" หรือ "เพิ่มยอดขายผ่านช่องทางออนไลน์"

2. ความต้องการของผู้ใช้ (User Requirements) ระดับผู้ใช้งานจริง

สิ่งที่ผู้ใช้งานคาดหวังว่าจะทำได้ผ่านระบบ เขียนด้วยภาษาธรรมชาติที่เข้าใจง่าย ไม่มีศัพท์เทคนิคคอมพิวเตอร์ เช่น "เจ้าหน้าที่ต้องการค้นหาประวัติการซื้อของลูกค้าได้ทันทีเมื่อรับสายโทรศัพท์"

3. ความต้องการของระบบ (System Requirements) ระดับทีมพัฒนา / วิศวกร

คำอธิบายเชิงโครงสร้างอย่างละเอียดถึงฟังก์ชันการทำงาน, อินพุต, เอาต์พุต, ฐานข้อมูล, และข้อจำกัดทางเทคนิค เช่น "ระบบต้องรองรับการค้นหาด้วย Customer_ID และแสดงผลลัพธ์ผ่านหน้า UI ภายในเวลาไม่เกิน 1.5 วินาที"

📌 บันทึกสำคัญ: เอกสาร SRS ที่สมบูรณ์ จะแปลง User Requirements ในชั้นที่ 2 ออกมาเป็น System Requirements ในชั้นที่ 3 อย่างละเอียดและครบถ้วน

ตารางเปรียบเทียบเชิงลึก: User Requirements vs. System Requirements

มิติการเปรียบเทียบ User Requirements (ความต้องการของผู้ใช้) System Requirements (ความต้องการของระบบ)
จุดมุ่งหมายหลัก (Primary Purpose) อธิบายภาพรวมว่า "ผู้ใช้ต้องการทำอะไรและได้ประโยชน์อะไร" ระบุอย่างชัดเจนว่า "ซอฟต์แวร์ต้องทำงานอย่างไร ต้องมีฟังก์ชันใดรองรับ"
ภาษาและรูปแบบ (Language & Notation) ภาษาธรรมชาติทั่วไป (Natural Language), แผนภาพง่ายๆ, User Stories ภาษาเทคนิคที่มีโครงสร้างทางการ (Structured English), Data Dictionaries, UML Diagrams
กลุ่มผู้อ่านหลัก (Target Audience) ลูกค้าผู้ว่าจ้าง, ผู้บริหารระดับสูง, ผู้ใช้งานระบบในชีวิตประจำวัน Software Engineers, Solution Architects, Developers, System Testers
ระดับความละเอียด (Detail Level) เชิงนามธรรม (Abstract), มุ่งเน้นกระบวนการทำงานระดับธุรกิจ (Business Flow) ละเอียดสูง (Concrete), ระบุฟิลด์ข้อมูล, รหัสข้อผิดพลาด, ข้อจำกัดเวลา
ตัวอย่างในระบบสุขภาพ "แพทย์ต้องสามารถดูประวัติการจ่ายยาของผู้ป่วยย้อนหลัง 5 ปีได้" "ระบบต้องดึงข้อมูลจากตาราง Medication_History ผ่าน REST API และส่งคืน JSON ไม่เกิน 500ms"
BOARD 02 / 06 SOMMERVILLE TAXONOMY • ISO 25010

การจำแนกประเภทความต้องการและตัวชี้วัด (Requirements Taxonomy & Quantitative Metrics)

สไลด์อ้างอิง: 11 - 16
การวัดผลเชิงคุณภาพสู่ตัวเลขเชิงวิศวกรรม
ฟังก์ชันการทำงาน WHAT IT DOES

1. Functional Requirements

ข้อกำหนดที่ระบุว่าระบบต้องให้บริการอะไร (Services) ต้องตอบสนองต่อสิ่งเร้าหรืออินพุตอย่างไร และในสภาวะจำเพาะระบบต้องทำอะไรหรือไม่ทำอะไร

• คำนวณภาษี: ระบบต้องคำนวณภาษีมูลค่าเพิ่ม 7% จากยอดรวมก่อนหักส่วนลด
• ยืนยันตัวตน: ระบบต้องส่ง OTP ทาง SMS เมื่อมีการล็อกอินจากอุปกรณ์ใหม่
คุณสมบัติและข้อจำกัด HOW WELL IT DOES

2. Non-Functional (NFR)

ข้อจำกัดด้านคุณภาพและมาตรฐานการดำเนินงาน (Constraints) เช่น ความเร็ว ความจุ ความปลอดภัย หาก NFR ไม่ผ่าน แม้ฟังก์ชันจะทำงานได้ ระบบก็อาจล้มเหลวทั้งระบบ

• ประสิทธิภาพ: รองรับผู้ใช้พร้อมกัน 10,000 คน โดยระบบไม่ล่ม
• ความปลอดภัย: รหัสผ่านต้องเข้ารหัสด้วย bcrypt salt rounds $\ge 12$
ข้อกำหนดเฉพาะทาง DOMAIN RULES

3. Domain Requirements

ความต้องการที่เกิดจากบริบทของสาขาวิชาชีพหรือกฎเกณฑ์เฉพาะทาง (Domain Context) เช่น การแพทย์ การเงิน หรือการบิน ซึ่งนักพัฒนาต้องปฏิบัติตามอย่างเคร่งครัด

• กฎหมายการเงิน: ระบบบัญชีต้องไม่ยอมให้ลบ Transaction แต่ใช้บันทึก Reversal แทน
• อัตราเบรกของรถไฟ: ต้องใช้สูตรคำนวณตามมาตรฐานความปลอดภัย UIC

โครงสร้าง 3 เสาหลักของความต้องการที่ไม่เป็นฟังก์ชัน (Sommerville NFR Classification)

📦 Product Requirements (ข้อกำหนดด้านผลิตภัณฑ์)

ระบุพฤติกรรมของตัวซอฟต์แวร์ที่ส่งมอบโดยตรง ประกอบด้วย:

  • Usability: ใช้งานง่าย เรียนรู้เร็ว หน้าตาไม่ซับซ้อน
  • Efficiency: ความเร็ว (Performance) และการใช้หน่วยความจำ (Space)
  • Reliability: อัตราการเกิดข้อผิดพลาดต่ำ (MTTF)
  • Portability: ทำงานได้ข้ามแพลตฟอร์ม (Windows, Mac, Linux, Mobile)
🏢 Organizational Requirements (ข้อกำหนดด้านองค์กร)

ระบุนโยบายและขั้นตอนปฏิบัติภายในองค์กรของผู้ว่าจ้างหรือผู้พัฒนา:

  • Environmental: ต้องรันบน Cloud Infrastructure ขององค์กร (เช่น AWS KMUTT)
  • Operational: ต้องเข้ากันได้กับระบบจัดการอัตลักษณ์เดิม (Active Directory)
  • Development: ต้องเขียนด้วยภาษา TypeScript และใช้ Git ในการคุมเวอร์ชัน
⚖️ External Requirements (ข้อกำหนดด้านภายนอก)

ปัจจัยภายนอกระบบและองค์กรที่ไม่สามารถหลีกเลี่ยงได้:

  • Regulatory & Legislative: กฎหมายคุ้มครองข้อมูลส่วนบุคคล (PDPA / GDPR)
  • Accounting: กฎเกณฑ์การบันทึกบัญชีของกรมสรรพากร
  • Safety & Ethical: มาตรฐานความปลอดภัยในชีวิตและทรัพย์สิน จริยธรรมการใช้งานข้อมูล

ตารางตัวชี้วัดเชิงปริมาณสำหรับ NFR (Quantitative Metrics for Verifiability)

เกณฑ์วัดที่ทดสอบได้จริง (Verifiable)

ข้อกำหนด NFR ที่ดีต้องไม่ใช้คำคุณศัพท์ที่เลื่อนลอย (เช่น "ต้องเร็ว", "ต้องใช้งานง่าย") แต่ต้องระบุเป็นหน่วยวัดเชิงปริมาณที่ตรวจสอบได้ดังตารางนี้:

คุณลักษณะ (Property) ตัวชี้วัด / มาตรวัด (Metric Specification) หน่วยวัดเชิงปริมาณ (Unit) ตัวอย่างการเขียนสเปกจริง
ความเร็ว (Speed) • จำนวนรายการประมวลผลต่อวินาที (Throughput)
• ระยะเวลาตอบสนองต่อคำสั่งผู้ใช้ (User Response Time)
• เวลาในการรีเฟรชหน้าจอ (Screen Refresh Time) 		วินาที (s), มิลลิวินาที (ms), Transactions/sec (TPS) "การประมวลผลคำสั่งค้นหาต้องแสดงผลภายในเวลา ≤ 2 วินาที ที่ 95th Percentile"
ขนาด (Size) • ขนาดพื้นที่ RAM / Storage ที่โปรแกรมใช้งาน
• ขนาดของ Application Binary หลังติดตั้ง
• จำนวนชิป ROM / Cache 		KiloBytes (KB), MegaBytes (MB), GigaBytes (GB) "ตัวติดตั้งระบบต้องมีขนาดไม่เกิน 50 MB บนอุปกรณ์พกพา"
ความง่ายในการใช้งาน (Ease of Use) • ระยะเวลาในการฝึกอบรมผู้ใช้ใหม่ให้เริ่มงานได้ (Training Time)
• จำนวนหน้าจอส่วนช่วยเหลือ (Help Frames)
• อัตราข้อผิดพลาดที่เกิดจากมนุษย์ (User Error Rate) 		ชั่วโมง (Hours), วัน (Days), สัดส่วนข้อผิดพลาด (%) "พนักงานใหม่ต้องสามารถสร้างใบสั่งซื้อได้ถูกต้องหลังอบรมไม่เกิน 2 ชั่วโมง"
ความน่าเชื่อถือ (Reliability) • ช่วงเวลาเฉลี่ยก่อนระบบขัดข้อง (MTTF - Mean Time To Failure)
• อัตราความพร้อมใช้งานของระบบ (Availability Rate)
• ความน่าจะเป็นที่ระบบล้มเหลวตามความต้องการ (POFOD) 		ชั่วโมง/วัน (Hours), อัตราความพร้อมใช้งาน (%) "ระบบต้องมีความพร้อมใช้งาน (Uptime) ไม่น้อยกว่า 99.95% ตลอด 24/7 (ล่มไม่เกิน 4.38 ชม./ปี)"
ความทนทาน (Robustness) • เวลาเฉลี่ยที่ใช้ในการกู้ระบบกลับคืน (MTTR - Mean Time To Repair)
• สัดส่วนข้อมูลที่สูญหายหลังเซิร์ฟเวอร์ไฟดับกะทันหัน 		นาที (Minutes to restart), % Data Loss "กรณีระบบหยุดทำงาน ต้องรีสตาร์ตและกลับมาให้บริการได้ภายใน 5 นาทีโดยไม่มีข้อมูลสูญหาย"
การย้ายระบบ (Portability) • สัดส่วนโค้ดที่สามารถนำไปรันบนระบบอื่นได้ทันที
• จำนวนระบบปฏิบัติการเป้าหมาย (Target Platforms) 		สัดส่วนร้อยละ (%), จำนวนระบบเป้าหมาย "ระบบต้องคอมไพล์และทำงานได้อย่างสมบูรณ์บนทั้ง Ubuntu 22.04 LTS และ Windows Server 2022"
BOARD 03 / 06 RE SPIRAL PROCESS • BABOK V3

กระบวนการวิศวกรรมความต้องการ (The 4-Stage RE Process: Elicitation & Analysis)

สไลด์อ้างอิง: 17 - 23
วงจรเกลียวสกัดและวิเคราะห์ความต้องการ
01 Discovery
1. การสกัดความต้องการ (Elicitation)

รวบรวมความต้องการจากผู้ใช้ ลูกค้า และสภาพแวดล้อม ด้วยการสัมภาษณ์ สังเกตการณ์ และเวิร์กช็อป

02 Refinement
2. การวิเคราะห์ความต้องการ (Analysis)

กลั่นกรอง ตรวจสอบความขัดแย้ง จัดลำดับความสำคัญ และแปลงเป็นโมเดลแนวคิด (DFD/ERD/UML)

03 Documentation
3. การจัดทำข้อกำหนด (Specification)

บันทึกเป็นเอกสารทางการตามมาตรฐาน IEEE 830 / ISO 29148 (SRS) ให้ชัดเจนและไม่กำกวม

04 Quality Gate
4. การตรวจทานความต้องการ (Validation)

ตรวจสอบความถูกต้อง ครบถ้วน สอดคล้อง และเป็นไปได้จริง ร่วมกับลูกค้าก่อนเริ่มเขียนโค้ด

เทคนิคการสกัดข้อมูล (Elicitation Techniques) ตามมาตรฐาน BABOK

การสกัดความต้องการไม่ได้หมายถึงแค่ "การถามแล้วจด" แต่ต้องใช้เครื่องมือผสมผสานเพื่อเจาะลึกความต้องการที่แท้จริง:

1. การสัมภาษณ์ (Interviews): • Closed Interviews: ถามตอบตามลิสต์คำถามที่กำหนดไว้ล่วงหน้าเพื่อเก็บข้อเท็จจริง
• Open Interviews: คุยแบบปลายเปิดเพื่อให้ผู้ใช้บรรยายปัญหาและขั้นตอนการทำงานโดยละเอียด
2. แบบสอบถามและการสำรวจ (Questionnaires & Surveys): เหมาะสำหรับระบบที่มีผู้ใช้งานจำนวนมาก กระจายตัวหลายสาขา ช่วยเก็บข้อมูลทางสถิติและลำดับความต้องการ
3. การสังเกตการณ์หน้างาน (Ethnography / Observation): ไปนั่งสังเกตพฤติกรรมการทำงานจริงของพนักงาน เพื่อค้นหา "ขั้นตอนแฝง (Implicit Tasks)" ที่ผู้ใช้มักลืมเล่าในห้องสัมภาษณ์

BOARD 04 / 06 IEEE STD 830-1998 • ISO/IEC/IEEE 29148

การจัดทำเอกสารข้อกำหนดความต้องการและมาตรฐาน IEEE 830 (SRS & Guidelines)

สไลด์อ้างอิง: 24 - 41
สัญญาข้อตกลงและพิมพ์เขียวการพัฒนา
Standard Evolution จาก IEEE Std 830 สู่มาตรฐานสากลสมัยใหม่

เอกสารข้อกำหนดความต้องการด้านซอฟต์แวร์ (Software Requirements Specification - SRS)

SRS เป็นเอกสารอย่างเป็นทางการที่บันทึกข้อตกลงร่วมกันระหว่างลูกค้าและทีมพัฒนา IEEE 830-1998 เป็นมาตรฐานโครงสร้างเอกสารคลาสสิกที่ใช้สอนในมหาวิทยาลัยทั่วโลก และในปัจจุบันได้ถูกรวมเป็นมาตรฐานร่วมสากล ISO/IEC/IEEE 29148:2018

โครงสร้างมาตรฐานของเอกสาร SRS ตาม IEEE 830 (Standard Outline)

1. บทนำ (Introduction)
  • 1.1 วัตถุประสงค์ของเอกสาร (Purpose)
  • 1.2 ขอบเขตผลิตภัณฑ์ (Scope)
  • 1.3 นิยามและอักษรย่อ (Definitions)
  • 1.4 เอกสารอ้างอิง (References)
  • 1.5 ภาพรวมส่วนอื่นๆ (Overview)
2. รายละเอียดทั่วไป (Overall)
  • 2.1 มุมมองผลิตภัณฑ์ (Perspective)
  • 2.2 ฟังก์ชันหลัก (Functions)
  • 2.3 คุณลักษณะผู้ใช้ (User Classes)
  • 2.4 ข้อจำกัดทั่วไป (Constraints)
  • 2.5 สมมติฐาน (Assumptions)
3. ข้อกำหนดเฉพาะ (Specific) ★
  • • ฟังก์ชันการทำงานทั้งหมด (Functional)
  • • ข้อกำหนดประสิทธิภาพ (NFR)
  • • การออกแบบฐานข้อมูล (Database)
  • • ส่วนต่อประสาน (UI & Hardware)
  • • ความปลอดภัย (Security / Safety)
4. ภาคผนวก (Appendices)
  • • ตารางแสดงผลการทดลอง
  • • รายละเอียดเชิงเทคนิคเฉพาะฮาร์ดแวร์
  • • ผังงานการไหลของข้อมูลส่วนขยาย
  • • ดัชนีคำค้นหา (Index)

8 คุณลักษณะของข้อกำหนดความต้องการที่ดี (Good SRS Criteria)

1. Correct (ถูกต้อง) ตรงกับความต้องการจริงของผู้ใช้ทุกประการ
2. Unambiguous (ไม่กำกวม) ทุกคนอ่านแล้วเข้าใจความหมายตรงกันทางเดียว
3. Complete (ครบถ้วน) ระบุทุกฟังก์ชัน ข้อจำกัด และการดักจับ Error
4. Consistent (สอดคล้องกัน) ไม่มีข้อกำหนดใดในเอกสารที่ขัดแย้งกันเอง
5. Ranked (จัดลำดับได้) บอกได้ว่าสิ่งใดสำคัญและเร่งด่วนกว่า
6. Verifiable (พิสูจน์ได้) มีตัวชี้วัดที่สร้างแบบทดสอบ (Test Case) ตรวจได้
7. Modifiable (แก้ไขได้ง่าย) โครงสร้างเป็นระบบ แก้จุดหนึ่งไม่ทำจุดอื่นพัง
8. Traceable (สืบย้อนได้) ตามรอยได้ว่าแต่ละข้อมาจากใครและแปลงเป็นโค้ดใด

ผู้มีส่วนเกี่ยวข้องกับการใช้ SRS (SRS Users Matrix)

ลูกค้า ใช้ระบุความต้องการ และตรวจสอบว่าตรงกับที่ให้ไว้หรือไม่ หากไม่ตรงสั่งแก้ไขทันที
ผู้จัดการ (PM) ใช้ประเมินงบประมาณ วางแผนตารางการทำงาน (Gantt Chart) และจัดสรรทีมงาน
วิศวกรระบบ ใช้ทำความเข้าใจภาพรวมและสถาปัตยกรรมระบบ เพื่อจัดแบ่งโมดูลการทำงาน
โปรแกรมเมอร์ ใช้เป็นพิมพ์เขียวในการเขียนโปรแกรมและออกแบบฐานข้อมูลให้ตรงตามข้อกำหนด
ผู้ทดสอบระบบ ใช้สร้างกรณีทดสอบ (Test Cases) เพื่อยืนยันว่าระบบทำงานถูกต้องตามสเปก

องค์ประกอบสำคัญในแบบฟอร์มข้อกำหนดเชิงฟังก์ชัน (Functional Specification Form)

1. User Stories / Use Cases
ระบุผู้ใช้, เงื่อนไขก่อนเริ่ม (Pre-condition), ลำดับเหตุการณ์ปกติ, และเส้นทางสำรอง (Alternate Flow)
2. UI Requirements
ภาพจำลองหน้าจอ (Mockup/Wireframe), ฟิลด์ข้อมูลที่ต้องกรอก, Validation Rules
3. Non-Functional Criteria
เวลาในการประมวลผลสูงสุดที่ยอมรับได้, สิทธิ์การเข้าถึง (RBAC), การเข้ารหัสข้อมูล
4. การอนุมัติ (Approvals)
ลงลายมือชื่อยืนยันระหว่างผู้ว่าจ้างและทีมพัฒนา เพื่อป้องกันปัญหา Scope Creep
BOARD 05 / 06 QUALITY GATES • COST ESCALATION

การตรวจทานความต้องการ (Requirement Validation & Quality Gates)

สไลด์อ้างอิง: 42 - 43
การสกัดจับจุดผิดพลาดก่อนต้นทุนพุ่งทะยาน

ทำไมต้องตรวจทานตั้งแต่ช่วงแรก? (The Cost-of-Fix Escalation Curve)

งานวิจัยของ Barry Boehm และ IBM Systems Sciences Institute ยืนยันว่า ยิ่งค้นพบและแก้ไขข้อผิดพลาดของ Requirement ช้าลงไปในเฟสท้ายๆ ต้นทุนในการแก้ไขจะพุ่งสูงขึ้นแบบก้าวกระโดด (Exponential):

1. ขั้นตอน Requirement (ต้นทุนต่ำสุด: 1x) ค่าใช้จ่าย: แก้ไขคำในเอกสาร SRS
2. ขั้นตอน Design & Architecture (5x) ค่าใช้จ่าย: แก้ผังฐานข้อมูลและ UML
3. ขั้นตอน Coding & Implementation (10x - 20x) ค่าใช้จ่าย: รื้อเขียนโค้ดและ Migrations
4. ขั้นตอน Production & Maintenance (50x - 100x+) ค่าใช้จ่าย: ระบบล่ม ลูกค้าฟ้อง เสียชื่อเสียง

3 เทคนิคหลักในการตรวจทานความต้องการ

1. การทบทวนความต้องการ (Requirement Reviews) ทีมผู้เชี่ยวชาญตรวจสอบเอกสารอย่างเป็นทางการ (Formal Fagan Inspection) และไม่เป็นทางการ (Peer Desk Check) เพื่อค้นหาความขัดแย้ง
2. การสร้างต้นแบบ (Prototyping) สร้างหน้าจอจำลอง (Mockup/Clickable Prototype) ให้ผู้ใช้ลองกดเล่นจริง เพื่อตรวจสอบว่าความเข้าใจตรงกันหรือไม่ก่อนลงมือเขียนโปรแกรม
3. การสร้างกรณีทดสอบ (Test-Case Generation) ออกแบบกรณีทดสอบล่วงหน้าตามแนวคิด Extreme Programming (XP) หากข้อกำหนดข้อใดไม่สามารถเขียน Test Case ได้ แสดงว่าข้อนั้นยังไม่ชัดเจน!

7 มิติการตรวจทานความถูกต้องของความต้องการ (Validation Checks Checklist)

1. Correctness (ความถูกต้อง)

ระบบตรงกับความต้องการที่แท้จริงของผู้ใช้หรือไม่ ผู้ใช้เห็นพ้องกับสเปกทั้งหมดหรือไม่

2. Consistency (ความสอดคล้อง)

ไม่มีข้อกำหนดใดขัดแย้งกัน เช่น หน้าหนึ่งบอกให้ส่ง SMS แต่อีกหน้าบอกไม่ให้ใช้เบอร์โทรศัพท์

3. Completeness (ความครบถ้วน)

ระบุครบทุกสถานการณ์ รวมถึงสภาวะผิดปกติ (Error Handling) และกรณีเน็ตเวิร์กหลุด

4. Realism (ความเป็นไปได้)

สามารถพัฒนาได้จริงภายใต้งบประมาณ เทคโนโลยี และกรอบเวลาที่โครงการกำหนด

5. Verifiability (พิสูจน์ได้)

สามารถออกแบบชุดทดสอบที่ให้ผลลัพธ์เป็น Pass/Fail ได้ชัดเจน ไม่เป็นความรู้สึกส่วนตัว

6. Clarity (ความชัดเจน)

ภาษาที่ใช้เขียนเรียบง่าย ตรงประเด็น ไม่ใช้คำศัพท์กำกวมที่ทำให้คนอ่านตีความได้หลายทาง

7. Traceability (ตรวจติดตามได้)

ทุกข้อกำหนดมีรหัส ID กำกับ (เช่น [REQ-01]) เพื่อสืบย้อนหาแหล่งที่มาและโมดูลโค้ดได้

ส่งกลับทีมวิเคราะห์แก้ไขทันที ห้ามปล่อยให้เริ่มงาน Design & Code เด็ดขาด!

ตามมาตรฐานวิศวกรรมซอฟต์แวร์ การเขียนข้อกำหนด System Requirement ในเอกสาร SRS ต้องใช้คำกริยาบังคับที่ชัดเจน เช่น "ระบบจะต้อง (The system shall...)" พร้อมตัวชี้วัดที่ไม่อึมครึม:
