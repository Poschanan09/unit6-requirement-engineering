ทำความเข้าใจปัญหาจริงของผู้ใช้ ก่อนเริ่มโค้ด
นิยามเข้าใจง่าย (Simple Definition) สไลด์หน้า 5

วิศวกรรมความต้องการ (Requirement Engineering) คือ กระบวนการที่ทีมวิศวกรซอฟต์แวร์ใช้ในการ "ค้นหา ทำความเข้าใจ สกัดข้อกำหนด และตรวจสอบความต้องการของลูกค้า" เพื่อนำมาสร้างเป็นเอกสารข้อกำหนดความต้องการ (SRS) สำหรับเป็นแบบแปลนในการสร้างระบบต่อไป

ทำไมถึงสำคัญมาก? (Why It Matters): ซอฟต์แวร์ส่วนใหญ่ไม่ได้พังเพราะเขียนโปรแกรมไม่เก่ง แต่พังเพราะ "สร้างผิดระบบตั้งแต่แรก (Building the wrong system)" การทำ Requirement ที่ดีคือการรับประกันว่า เรากำลังแก้ปัญหาที่ถูกต้องของลูกค้า

RE ในวัฏจักรการพัฒนาซอฟต์แวร์ (SDLC 7 ขั้นตอน)

สไลด์หน้า 3 (สุวรรณี, 2561)

ตามสไลด์ของวิชา SDLC ประกอบด้วย 7 ขั้นตอน โดย Requirement อยู่ในขั้นตอนที่ 3:

  1. 1 การกำหนดปัญหา (Problem Definition): กำหนดขอบเขตปัญหาที่ต้องการแก้ไข
  2. 2 การศึกษาความเป็นไปได้ (Feasibility Study): เทคโนโลยี, งบประมาณ, ความคุ้มค่า
  3. 3
    ความต้องการของผู้ใช้ (User Requirement) ★
    หัวใจของ Unit 6: แปลงความต้องการของผู้ใช้สู่สเปกระบบ
  4. 4 การวิเคราะห์และออกแบบระบบ (System Analysis and Design): DFD, ERD, UML
  5. 5 การเขียนโปรแกรม (Programming): ลงมือเขียนโค้ดตามผลการออกแบบ
  6. 6 การทดสอบโปรแกรม (Testing): ตรวจสอบว่าโปรแกรมทำงานตามสเปกหรือไม่
  7. 7 การบำรุงรักษาโปรแกรม (Software Maintenance): ปรับปรุง แก้ไขบั๊กตามการใช้งาน

การเชื่อมต่อระบบเดิมสู่ระบบใหม่: AS-IS vs. TO-BE

สไลด์หน้า 6

การเก็บ Requirement ไม่ใช่การนั่งเทียนคิดระบบใหม่จากความว่างเปล่า แต่ต้องผ่าน 3 สเต็ป:

Step 1 • AS-IS System

ทำความเข้าใจระบบปัจจุบัน (Understand the existing system)

ศึกษาว่าปัจจุบันผู้ใช้ทำงานอย่างไร ใช้กระดาษหรือระบบเดิมตรงไหน มีปัญหาอุปสรรคอะไรบ้าง

Step 2 • Identify Improvement

ระบุจุดที่ต้องการปรับปรุงแก้ไข

วิเคราะห์ว่ามีจุดใดที่ล่าช้า ผิดพลาดบ่อย หรือมีต้นทุนสูงเกินไป

Step 3 • TO-BE System

กำหนดความต้องการของระบบใหม่ (Define Requirements for new system)

ออกแบบระบบใหม่ที่จะเข้ามาทดแทนหรือเสริมการทำงานให้มีประสิทธิภาพสูงสุด

💡 ตัวอย่างเชื่อมโยง: ระบบลงทะเบียนเรียนเดิม (AS-IS) ให้นักศึกษากรอกกระดาษแล้วต่อคิวที่ทะเบียน → จุดปรับปรุง: คิวยาว ตรวจสอบวิชาพรีไม่ทัน → ระบบใหม่ (TO-BE): ลงทะเบียนผ่านเว็บออนไลน์พร้อมตรวจสอบเงื่อนไขวิชาอัตโนมัติ

ตารางเปรียบเทียบ: User Requirements vs. System Requirements (สไลด์หน้า 8 - 10)

ข้อสอบออกบ่อยมาก! ★

ความต้องการด้านซอฟต์แวร์ถูกแบ่งออกเป็น 2 ระดับความต้องการ (2 Levels of Requirements) เพื่อสื่อสารกับคนที่แตกต่างกัน:

ประเด็นการเปรียบเทียบ 1. ความต้องการของผู้ใช้ (User Requirements) 2. ความต้องการด้านระบบ (System Requirements)
นิยาม (Definition) ความต้องการหรือความคาดหวังที่ผู้ใช้คาดว่าจะได้รับจากซอฟต์แวร์ตามเงื่อนไขการทำงาน ความต้องการของระบบในระดับรายละเอียดการทำงาน ฟังก์ชัน และบริการเพื่อตอบสนองผู้ใช้
ภาษาที่ใช้ (Language) ภาษาธรรมชาติ (Natural Language) เข้าใจง่าย ไม่ระบุรายละเอียดทางเทคนิค ภาษาเชิงเทคนิค มีโครงสร้างมาตรฐาน ไม่อธิบายด้วยภาษาธรรมชาติแบบผู้ใช้
กลุ่มผู้อ่าน (Target Audience) ผู้ใช้งานระบบ, ผู้ว่าจ้าง, ผู้บริหาร วิศวกรซอฟต์แวร์, โปรแกรมเมอร์, ผู้ทดสอบระบบ (Testers)
ระดับรายละเอียด (Detail Level) ภาพรวมฟังก์ชัน หน้าตาระบบ และความสามารถหลัก ลงลึกในรายละเอียดว่า "อะไรควรทำ อะไรไม่ควรทำ อะไรคือข้อยกเว้นและเงื่อนไข"
เอกสารที่บันทึก (Document) Requirement Specification (User Requirement Document) System Requirement Specification (SRS)
ตัวอย่างระบบ Call Center "พนักงานต้องการดูข้อมูลผู้โทรมาร้องเรียนได้อย่างรวดเร็ว" "ระบบต้องดึงประวัติการโทรจากตาราง Complaints ด้วยเบอร์โทรเข้า และแสดงผลภายใน 1 วินาที"
📝 จำไปสอบ (Board 1)
  • SDLC มี 7 ขั้นตอน: Requirement อยู่ในขั้นตอนที่ 3
  • เป้าหมายของ RE คือ "สร้างและบำรุงรักษาเอกสารข้อกำหนดความต้องการที่มีคุณภาพ"
  • User Requirement = ภาษาธรรมชาติ / ผู้ใช้อ่าน vs System Requirement = ภาษาเทคนิค / Dev อ่าน
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

ระวัง: ข้อสอบมักถามว่า "System Requirement ควรเขียนด้วยภาษาธรรมชาติเพื่อให้ทุกคนเข้าใจตรงกันใช่หรือไม่?" → ตอบ: ไม่ใช่! ภาษาธรรมชาติใช้กับ User Requirement ส่วน System Requirement ต้องใช้ภาษาเทคนิคที่มีโครงสร้างทางการชัดเจนเพื่อไม่ให้กำกวม

3 ประเภทของความต้องการด้านซอฟต์แวร์ระบบ (ตามสไลด์หน้า 9 และ 11)

เนื้อหาทางการจากสไลด์
หน้าที่หลัก TYPE 1

1. ความต้องการเชิงฟังก์ชัน (Functional Requirement)

ความต้องการที่ให้ซอฟต์แวร์ระบบทำหน้าที่ตามที่กำหนด ซึ่งเป็นหน้าที่หลักที่ซอฟต์แวร์นั้นๆ ควรมี (What the system should do)

• ตัวอย่าง: บันทึกรายละเอียดลูกค้า, ค้นหาข้อมูลสินค้า, คำนวณยอดเงินรวม, ส่งข้อความเตือน
คุณสมบัติส่งเสริม TYPE 2

2. ความต้องการที่ไม่เป็นฟังก์ชัน (Non-Functional Requirement)

ความต้องการที่ไม่ได้เกี่ยวกับหน้าที่หลักโดยตรง แต่เกี่ยวข้องทางอ้อมเพื่อส่งเสริมให้ระบบทำงานได้มีประสิทธิภาพมากขึ้น เช่น น่าเชื่อถือ ปลอดภัย รวดเร็ว ถูกกฎหมาย

• ตัวอย่าง: ตอบสนองภายใน 1 วินาที, รองรับคนพร้อมกัน 5,000 คน, เข้ารหัสผ่านตามมาตรฐาน
เฉพาะธุรกิจ TYPE 3

3. ความต้องการด้านธุรกิจ (Business Requirement)

ความต้องการที่เกี่ยวข้องกับงานหลักของระบบธุรกิจ ซึ่งเป็นความต้องการเฉพาะของธุรกิจนั้นๆ ที่นำซอฟต์แวร์มาสนับสนุน (เป็นได้ทั้งเชิงฟังก์ชันและไม่เป็นฟังก์ชัน)

• ตัวอย่าง: ลดขั้นตอนการเคลมประกันเหลือ 1 วัน, โปรโมชันลดราคาเฉพาะเทศบาล 12.12

3 กลุ่มย่อยของ Non-Functional Requirements (ตาม Sommerville สไลด์หน้า 11 - 12)

Sommerville (2016) 10th Ed.
📦 1. ด้านผลิตภัณฑ์ (Product Requirement)

ข้อกำหนดด้านพฤติกรรมของตัวซอฟต์แวร์โดยตรง ประกอบด้วย:

  • ประสิทธิภาพ (Performance): ระยะเวลาตอบสนอง, ขนาดหน่วยความจำ
  • ความน่าเชื่อถือ (Reliability): อัตราความผิดพลาดที่ยอมรับได้
  • การทำงานข้ามแพลตฟอร์ม (Portability): ใช้งานบนอุปกรณ์/ระบบที่ต่างกัน
  • ใช้งานง่าย (Usability): ความสะดวกในการเรียนรู้และใช้งาน
🏢 2. ความต้องการองค์กร (Organizational Requirement)

ข้อตกลงระหว่างองค์กรกับผู้พัฒนา เพื่อให้เป็นแนวทางตรงกัน:

  • มาตรฐานการพัฒนา (Standards): วิธีการเขียนโค้ด, การออกแบบสถาปัตยกรรม
  • ภาษาและเทคโนโลยี: ภาษาโปรแกรมหรือเฟรมเวิร์กที่องค์กรกำหนด
  • กระบวนการส่งมอบ (Delivery): กำหนดการส่งมอบงาน, แผนการอบรมบุคลากร
⚖️ 3. ปัจจัยภายนอก (External Requirement)

ปัจจัยภายนอกที่ส่งผลกระทบต่อกระบวนการพัฒนา:

  • การทำงานร่วมกัน (Interoperability): การเชื่อมต่อกับระบบภายนอกอื่นๆ
  • ข้อกำหนดทางกฎหมาย (Legislative): ไม่ละเมิดลิขสิทธิ์, ไม่ขัดหลัก PDPA
  • หลักจริยธรรม (Ethical Requirements): เป็นที่ยอมรับได้ของผู้ใช้และสังคม

ตัวชี้วัดสำหรับความต้องการที่ไม่เป็นฟังก์ชัน (NFR Metrics Table - สไลด์หน้า 13)

*คัดลอกนิยามคุณลักษณะและหน่วยวัดตรงตามสไลด์หน้า 13 ของอาจารย์แบบ 100%:

คุณลักษณะ (Property) หน่วยวัดตามสไลด์อาจารย์ (Measurement Units)
ความเร็ว (Speed) • การประมวลผลรายการข้อมูล (หน่วยนับ: วินาที) (Processed transactions/second)
• ระยะเวลาตอบสนอง (User/event response time)
• เวลาในการเปลี่ยนข้อมูลบนจอภาพ (Screen refresh time)
ขนาด (Size) • ขนาด MB (Megabytes), GB etc.
• จำนวน Memory (Number of ROM chips)
ใช้งานง่าย (Ease of use) • ระยะเวลาที่ใช้ในการอบรมสำหรับการใช้งาน (Training time)
• จำนวนของส่วนช่วยเหลือ (Number of help frames)
ความน่าเชื่อถือ (Reliability) • ค่าเฉลี่ยของข้อผิดพลาดที่เกิดขึ้น (Mean time to failure)
• ความน่าจะเป็นของระบบที่ไม่สามารถใช้งานได้ (Probability of unavailability)
• อัตราการเกิดข้อผิดพลาด (Rate of failure occurrence)
• อัตราที่ระบบใช้งานได้ (Availability)
ความทนทาน (Robustness) • จำนวนครั้งที่รีสตาร์ทหลังจากเกิดความล้มเหลว (Time to restart after failure)
• เปอร์เซ็นต์ของเหตุการณ์ที่ทำให้เกิดความล้มเหลว (Percentage of events causing failure)
• ความน่าจะเป็นของความเสียหายของข้อมูลเมื่อล้มเหลว (Probability of data corruption on failure)
ความสามารถในการทำงานข้ามระบบ (Portability) • เปอร์เซ็นต์ของระบบที่ขึ้นต่อกัน (Percentage of target dependent statement)
• จำนวนของระบบอื่นๆ ที่สามารถทำงานร่วมกันได้ (Number of target systems)

ตัวอย่างที่ 1: ระบบ "การจัดเก็บข้อมูลลูกค้า" (สไลด์ 15)
Functional Requirements (หน้าที่หลัก):
  1. มีหน้าจอให้ลูกค้าบันทึกรายละเอียดประจำตัวบุคคล/นิติบุคคล ได้ด้วยตนเอง
  2. ลูกค้าสามารถใช้งานผ่านเครือข่าย Internet ได้
  3. ระบบยืนยันตัวตนคนไทย/นิติบุคคล ผ่านระบบภาครัฐ (สพร. / DGA)
  4. เชื่อมต่อฐานข้อมูลบัตรประชาชนกับกรมการปกครอง เพื่อดึงข้อมูลที่จำเป็น
Non-Functional Requirements (เงื่อนไขเสริม):
  1. หลีกเลี่ยงการจัดเก็บข้อมูลที่ไม่จำเป็น และไม่ขัดกับ พรบ. คุ้มครองข้อมูลส่วนบุคคล (PDPA)
  2. ให้ลูกค้าคีย์ข้อมูลให้น้อยที่สุดเพื่อลดความผิดพลาด (ใช้ Dropdown ตัวเลือก)
  3. ออกแบบเผื่อการเชื่อมโยงแลกเปลี่ยนข้อมูลกับหน่วยงานอื่นในอนาคต
  4. หากเครือข่ายขัดข้อง ต้องสรุปปัญหาพร้อมแนวทางแก้ไขภายใน 2 ชั่วโมง
ตัวอย่างที่ 2: ความต้องการ "ระบบ Call Center" (สไลด์ 16)
Functional Requirements (หน้าที่หลัก):
  1. จัดการสิทธิ์ผู้ใช้งานหลายระดับ: Supervisor, Agent, Super Admin, Admin, User, Guest
  2. รับเรื่องร้องเรียนได้หลายช่องทาง: Social Network, SMS, Phone call, Voice, FB, Line
  3. รวบรวมเรื่องร้องเรียน จัดกลุ่ม และจัดหมวดหมู่ลงระบบ
  4. จัดทำรายงานตามกลุ่ม, ช่วงวัน, อายุผู้ร้อง, จังหวัด, จำนวนเรื่อง
Non-Functional Requirements (เงื่อนไขเสริม):
  1. ช่องทางร้องเรียนต้องแสดง ICON ให้สังเกตง่าย (เช่น รูปโทรศัพท์มือถือ/บ้าน)

หัวใจ: Elicitation & Analysis

ลำดับ 4 ขั้นตอนหลักของกระบวนการวิศวกรรมความต้องการ (สไลด์หน้า 18)

ต้องท่องลำดับให้ถูก
01
1. Requirement Elicitation
การสกัดความต้องการ

รวบรวมและค้นหาความต้องการ ทำความเข้าใจปัญหาที่เกิดขึ้น กำหนดกลุ่มบุคคลที่เกี่ยวข้อง และรวบรวมด้วยเทคนิคต่างๆ

02
2. Requirement Analysis
การวิเคราะห์ความต้องการ

ประเมินความต้องการ จัดกลุ่ม จัดลำดับความสำคัญ สร้างแบบจำลองแนวคิด (Conceptual Model) และนำเสนอเพื่อขอการยอมรับ

03
3. Requirement Specification

หลังจากแบบจำลองได้รับการยอมรับ นำมาจัดทำเป็นเอกสารข้อกำหนดความต้องการอย่างเป็นทางการ (SRS ตามมาตรฐาน IEEE 830)

04
4. System Requirement Validation
การตรวจทานความต้องการ

ทบทวนและตรวจสอบเอกสารทั้งหมด เพื่อความเที่ยงตรง สอดคล้อง สมบูรณ์ เป็นไปได้จริง และพิสูจน์ได้ตามเป้าหมาย

7 เทคนิคในการสกัด/เก็บรวบรวมความต้องการ (สไลด์หน้า 19 - 20)

ออกข้อสอบทั้ง 7 ข้อ

ในสไลด์ของอาจารย์ระบุเทคนิคการสกัดข้อมูลไว้ทั้งหมด 7 วิธี ดังนี้:

1. การสัมภาษณ์ (Interview)

เป็นวิธีที่ดั้งเดิมและนิยมใช้มากที่สุดวิธีหนึ่ง เป็นการสอบถาม พูดคุยระหว่างทีมพัฒนากับผู้ใช้ (สิ่งสำคัญ: ผู้สัมภาษณ์ต้องเปิดใจรับฟัง)

2. ลำดับเหตุการณ์ (Scenario)

เตรียมคำถามตามลำดับงาน เช่น "จะเกิดอะไรขึ้นถ้า... และจะทำเช่นไร อย่างไร" เชื่อมโยงสู่แบบจำลองลักษณะ Use Case

3. ต้นแบบ (Prototype)

ทำให้ผู้ใช้เข้าใจระบบงานได้ง่าย ออกแบบบนกระดาษ โปรแกรม หรือโมเดลจำลอง เพื่อทดสอบการยอมรับของความต้องการในเบื้องต้น

4. การประชุม (Facilitated Meeting)

ประชุมกลุ่มผู้เกี่ยวข้องเพื่อระดมความคิดเมื่อพบข้อขัดแย้ง วิธีนี้ได้ข้อมูลคุณภาพสูงมาก แต่ต้องระวังความขัดแย้งระหว่างบุคคลหรือทีม

5. การสังเกต (Observation)

ตรวจสอบสภาพแวดล้อม ปัญหา อุปสรรค และวิธีแก้ไขจริงของผู้ใช้ระบบเดิม (ข้อควรระวัง: มีค่าใช้จ่ายสูงมากกว่าวิธีอื่น)

6. เอกสารเดิม (Existing Documents)

วิเคราะห์จากเอกสาร แบบฟอร์ม ฐานข้อมูลเดิม ผังงาน รายงาน และคู่มือระบบเดิมที่องค์กรมีอยู่

7. แบบสอบถาม (Questionnaire)

ใช้รวบรวมข้อมูลจากคนจำนวนมาก ประกอบด้วยคำถามปลายเปิดและคำถามปลายปิด

กรอบการตั้งคำถาม 5W1H: ระบบปัจจุบัน vs ระบบใหม่ (สไลด์หน้า 21)

โอภาส เอี่ยมสิริวงศ์ (2566)
คำถาม ระบบปัจจุบัน (AS-IS) ระบบใหม่ (TO-BE)
Who? (ใคร) ใครเป็นผู้ทำ? แล้วทำไมบุคคลนี้ถึงเป็นผู้ทำ? ผู้สมควรทำ... ควรเป็นใคร?
What? (อะไร) ทำอะไร? แล้วทำไปทำไม? สิ่งที่ควรทำ มีอะไรบ้าง?
Where? (ที่ไหน) ทำที่ไหน? แล้วทำไมจึงต้องทำที่นั่น? ควรจะทำที่ไหน?
When? (เมื่อไหร่) ทำเมื่อไหร่? แล้วทำไมต้องทำ? ควรจะทำเมื่อไหร่?
How? (อย่างไร) ทำอย่างไร? แล้วทำไมต้องทำแบบนั้น? ควรจะทำอย่างไร?
Why? (ทำไม) ทำไมคิดว่าระบบใหม่จะช่วยแก้ปัญหาได้?

Analysis Activities
2.1 จัดกลุ่มความต้องการ (Classification):

แยก Functional vs Non-Functional, จัดลำดับ (จำเป็น/ปรารถนาสูง/ปานกลาง/ละเว้นได้), ขอบเขตกว้าง vs แคบ

2.2 สร้างแบบจำลองแนวคิด (Conceptual Model):

สร้าง DFD, ERD, UML, Use Case Diagram, Class/Object Diagram เพื่อสื่อสารกับผู้ใช้

2.4 ออกแบบสถาปัตยกรรมและจัดสรร (Allocation):

จัดสรรความต้องการ (Requirement Allocation) เข้ากับสถาปัตยกรรมซอฟต์แวร์

2.5 เจรจาต่อรองความต้องการ (Negotiation):

แก้ไขข้อขัดแย้ง (Conflict Resolution) เมื่อผู้มีส่วนได้ส่วนเสียต้องการไม่ตรงกัน หรือทรัพยากรไม่เพียงพอ

  • เทคนิคที่คุณภาพสูงแต่ระวังขัดแย้ง = การประชุม (Facilitated Meeting)

เอกสาร 3 ชนิดในขั้นตอนการจัดทำข้อกำหนด (สไลด์หน้า 24)

ในระบบขนาดใหญ่ที่มีความซับซ้อนสูง จะประกอบด้วยเอกสาร 3 ชนิด:

1. เอกสารนิยามระบบ (System Definition): หรือ User Requirement Document บันทึกความต้องการของผู้ใช้ ใช้ภาษาที่เข้าใจง่าย ไม่เน้นเทคนิค
2. ข้อกำหนดด้านระบบ (System Req Spec): อธิบายการดำเนินการด้านวิศวกรรมระบบ ถูกกำหนดก่อนและแยกออกจากเอกสารซอฟต์แวร์
3. ข้อกำหนดซอฟต์แวร์ (SRS) ตาม IEEE 830: ระบุหน้าที่ของซอฟต์แวร์ เป็นข้อตกลงพื้นฐานระหว่างทีมพัฒนากับผู้ใช้งาน (ถ้าระบบไม่ซับซ้อน อาจมีแค่ SRS อย่างเดียว)

8 คุณลักษณะของข้อกำหนดความต้องการที่ดี (สไลด์หน้า 27)

ต้องท่องจำ 8 ข้อ

ตามมาตรฐาน IEEE 830 ข้อกำหนดที่ดีต้องมีครบทั้ง 8 ข้อ:

1. Correct (ถูกต้อง) ตรงกับความต้องการจริงของผู้ใช้
2. Unambiguous (ไม่กำกวม) มีความหมายเดียว ตีความเป็นอื่นไม่ได้
3. Complete (ครบถ้วน) มีทุกฟังก์ชัน ข้อจำกัด และดักจับ Error
4. Consistent (สอดคล้องกัน) ไม่มีข้อกำหนดใดในเอกสารที่ขัดแย้งกัน
5. Ranked (จัดลำดับได้) บอกได้ว่าข้อใดสำคัญ/จำเป็นกว่า
6. Verifiable (พิสูจน์ได้) มีวิธีทดสอบที่บอกผล Pass/Fail ชัดเจน
7. Modifiable (แก้ไขได้ง่าย) แก้จุดหนึ่ง ไม่กระทบให้จุดอื่นพัง
8. Traceable (สืบย้อนได้) สืบย้อนหาที่มาและโมดูลโค้ดได้
⚠️ ระวังอย่าสับสน: 8 ข้อนี้คือ "คุณลักษณะของข้อกำหนดที่ดีตาม IEEE 830" ส่วนใน Board 5 จะเป็น "7 คุณลักษณะในการตรวจทาน (Validation Criteria)" ซึ่งใกล้เคียงกันแต่อยู่คนละสไลด์!

การตรวจทานความต้องการ คือ "การทบทวนและตรวจสอบข้อกำหนดความต้องการในเอกสารทั้งหมด เพื่อความเที่ยงตรง สอดคล้อง สมบูรณ์ เป็นไปได้ และพิสูจน์ได้ตามเป้าหมาย" เพื่อให้มั่นใจว่าระบบจะตรงกับความต้องการจริงของผู้ใช้ก่อนเข้าสู่ขั้นตอนการออกแบบระบบ (System Design)

7 ด้านที่ต้องตรวจสอบในการตรวจทานความต้องการ (สไลด์หน้า 42)

จำนิยามภาษาไทยให้แม่น! ★
1. Correctness (ความถูกต้อง)

ความต้องการสามารถแสดงมุมมองของผู้ใช้งานระบบที่ตรงกัน

2. Consistency (ความต้องกัน / สอดคล้อง)

ความต้องการทั้งเชิงฟังก์ชันและไม่เป็นฟังก์ชันในเอกสารไม่ทับซ้อนกัน ไม่ขัดแย้ง ต้องเป็นไปในแนวทางเดียวกันทั่วทั้งเอกสาร

3. Completeness (ความครบถ้วนสมบูรณ์)

ต้องระบุรายละเอียดฟังก์ชันและความต้องการอย่างครบถ้วนไม่ตกหล่น และครอบคลุมความต้องการผู้ใช้

4. Realism (ความเป็นจริง)

ความต้องการถูกนำไปสร้างได้จริงตามความต้องการของผู้ใช้งานระบบ (เทคโนโลยี, เวลา, งบประมาณ)

5. Verifiability (สามารถพิสูจน์ได้)

ความต้องการนั้นต้องพิสูจน์เพื่อหาความจริงได้ คือทดสอบ/ทดลองได้ เพื่อลดข้อโต้แย้งระหว่างทั้ง 2 ฝ่าย

6. Clarity (ความชัดเจน)

ความต้องการไม่คลุมเครือ ไม่กำกวม

7. Traceability (การตรวจติดตาม)

สามารถสืบย้อนหาแหล่งที่มาและติดตามความสัมพันธ์ของข้อกำหนดได้

กฎเหล็ก (Slide 43): หากพบข้อผิดพลาด ต้องส่งกลับให้ทีมพัฒนาแก้ไขให้เรียบร้อย ก่อนนำไปสู่ออกแบบ!

3 เทคนิคที่ใช้ในการตรวจทานความต้องการ (สไลด์หน้า 43)

Validation Techniques
1. การทบทวนความต้องการ (Requirement Review)

ตรวจสอบเอกสารอย่างละเอียด เพื่อค้นหาจุดผิดพลาดไม่ตรงตามข้อกำหนด แบ่งเป็น:

  • แบบทางการ (Formal Review): ตั้งคณะกรรมการตรวจสอบตามวาระอย่างเป็นระบบ
  • แบบไม่เป็นทางการ (Informal Review): เพื่อนร่วมทีมช่วยตรวจทาน (Peer Review)
2. การจัดทำต้นแบบ (Prototyping)

สร้างระบบจำลองหรือ Mockup หน้าจอขึ้นมา "เพื่อสาธิตให้ผู้ใช้ระบบเห็นภาพ หรือให้ทดลองใช้ด้วยตนเอง" ช่วยจับจุดที่เข้าใจไม่ตรงกันได้ดีที่สุด

3. การสร้างกรณีทดสอบ (Test-Case Generation)

จำลองเหตุการณ์หรือข้อมูลเพื่อการทดสอบเป็นรายกรณี (Case) โดยสไลด์ระบุว่า "ใช้เทคนิค Extreme Programming (XP)"

💡 ถ้า Requirement ข้อไหนไม่สามารถเขียน Test Case ได้ แสดงว่าข้อนั้นยังไม่ชัดเจนหรือพิสูจน์ไม่ได้!

✍️ ตัวอย่างการแก้โจทย์: เปลี่ยนข้อกำหนดที่กำกวม (Vague) ให้พิสูจน์ได้ (Verifiable)

❌ ข้อกำหนดที่กำกวม (ไม่ผ่านเกณฑ์ Verifiability):
"ระบบจะต้องค้นหาข้อมูลลูกค้าได้อย่างรวดเร็ว และหน้าจอต้องใช้งานง่าย"
เหตุผลที่ไม่ผ่าน: คำว่า "รวดเร็ว" กับ "ใช้งานง่าย" เป็นความรู้สึก ไม่มีหน่วยวัด ไม่สามารถเขียน Test Case ได้
✅ ปรับแก้ให้ผ่านเกณฑ์ (Verifiable & Unambiguous):
"ระบบจะต้องแสดงผลลัพธ์การค้นหาลูกค้าภายในเวลาไม่เกิน 1.0 วินาที และผู้ใช้ใหม่ต้องสามารถทำรายการสำเร็จได้หลังจากผ่านการฝึกอบรมไม่เกิน 15 นาที"
ผ่านเกณฑ์: มีหน่วยวัดเป็นวินาทีและนาที ทดสอบแบบ Pass/Fail ได้ชัดเจน!
📝 จำไปสอบ (Board 5)
  • 7 เกณฑ์ตรวจสอบ: Correctness, Consistency, Completeness, Realism, Verifiability, Clarity, Traceability
  • 3 เทคนิค: Requirement Review (Formal/Informal), Prototyping, Test-Case Generation (XP)
  • หากพบข้อผิดพลาด ต้องส่งกลับให้ทีมพัฒนาแก้ไขก่อนเริ่มขั้นตอนออกแบบระบบ (Design)
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

ระวัง: ข้อสอบมักถามว่า "เทคนิคการสร้าง Test-Case ในสไลด์อ้างอิงแนวคิดใด?" → ตอบ: Extreme Programming (XP)

🎓 กรณีศึกษาที่ 2: ความต้องการ "ระบบลงทะเบียนเรียน" (สไลด์ 51 - 53)

โอภาส เอี่ยมสิริวงศ์ (2566), การวิเคราะห์และออกแบบระบบ

สไลด์ 51 - 53

ตัวอย่างการนำฟอร์ม Standard Form: System Requirement Specification (Function Spec) มาใช้กับระบบลงทะเบียน:

Function: บันทึกการลงทะเบียนรายวิชา (Course Registration)
Stakeholders: นักศึกษา, อาจารย์ที่ปรึกษา, เจ้าหน้าที่ทะเบียน
Brief Description: ฟังก์ชันสำหรับให้นักศึกษาเลือกรายวิชา ตรวจสอบเงื่อนไขวิชาบังคับก่อน และยืนยันการลงทะเบียนเรียนในแต่ละภาคการศึกษา
Input: รหัสนักศึกษา, รหัสวิชา, กลุ่มเรียน (Section)
Source: แบบฟอร์มหน้าจอลงทะเบียนเรียน
Output: ใบเสร็จยืนยันผลการลงทะเบียน, ตารางเรียนประจำตัว
Requires: ระบบฐานข้อมูลทะเบียนกลาง, ระบบตัดเงินออนไลน์
Preconditions: นักศึกษาชำระค่าธรรมเนียมแรกเข้าแล้ว และอยู่ในช่วงเวลาลงทะเบียน
Postcondition: จำนวนที่นั่งในวิชานั้นถูกตัดลดลง 1 ที่ และบันทึกประวัติการลงทะเบียน
Main Flow (ขั้นตอนการทำงานหลัก):
  1. นักศึกษาล็อกอินเข้าสู่ระบบด้วยบัญชีมหาวิทยาลัย
  2. เลือกรายวิชาและกลุ่มเรียนที่เปิดสอน
  3. ระบบตรวจสอบเงื่อนไขวิชาบังคับก่อน (Prerequisite) และการชนกันของเวลาเรียน
  4. ระบบตัดยอดที่นั่งและแสดงหน้าต่างยืนยันผลการลงทะเบียน
Exception Conditions (เงื่อนไขข้อยกเว้น):
  • หากที่นั่งในกลุ่มเรียนเต็ม → ระบบแจ้งเตือนให้เลือกกลุ่มอื่นหรือยื่นคำร้องขอเปิดกลุ่มพิเศษ
  • หากไม่ผ่านวิชาบังคับก่อน → ระบบปฏิเสธการลงทะเบียนพร้อมระบุวิชาที่ต้องเรียนก่อน
  • หากเกิดปัญหาเครือข่ายขัดข้องระหว่างบันทึก → ระบบ Rollback ข้อมูลกลับคืนโดยไม่ตัดที่นั่ง
📝 จำไปสอบ (Board 6)
  • การแปลงความต้องการต้องเริ่มจาก Scenario → Use Case → Use Case Diagram → Activity Diagram → Class & State Diagrams
  • Use Case ต้องระบุทั้ง Main Flow (ปกติ) และ Exception Conditions (ข้อยกเว้น)
⚠️ จุดที่ข้อสอบชอบหลอก (Exam Trap)

ระวัง: Use Case ไม่ใช่โค้ดโปรแกรม แต่เป็นคำอธิบายปฏิสัมพันธ์ระหว่างผู้ใช้ (Actor) กับระบบ เพื่อให้ทุกฝ่ายเข้าใจตรงกันก่อนเขียน Class Diagram

[ข้อสอบ 1 - MCQ] ข้อใดกล่าวถึงความแตกต่างระหว่าง User Requirements และ System Requirements ได้อย่างถูกต้องที่สุด?
▶
ก. User Requirements อธิบายด้วยภาษาเทคนิค ส่วน System Requirements ใช้ภาษาธรรมชาติ
ข. User Requirements ใช้ภาษาธรรมชาติสำหรับผู้ใช้งาน ส่วน System Requirements ใช้ภาษาเชิงเทคนิคสำหรับนักพัฒนา

ง. User Requirements จัดทำโดยโปรแกรมเมอร์ ส่วน System Requirements จัดทำโดยลูกค้า

ก. Functional Requirement ด้านประสิทธิภาพ
ข. Non-Functional Requirement ด้านผลิตภัณฑ์ (Product Requirement)
ค. Non-Functional Requirement ด้านองค์กร (Organizational Requirement)

[ข้อสอบ 4 - MCQ] เทคนิคการสกัดความต้องการ (Elicitation) ในข้อใด ที่สไลด์ระบุว่า "มีค่าใช้จ่ายสูงมากกว่าวิธีการอื่น"?
▶
ก. การสัมภาษณ์ (Interview)
ข. การสร้างต้นแบบ (Prototype)
ค. การสังเกตการณ์ (Observation)
ง. แบบสอบถาม (Questionnaire)
เฉลย ค. สไลด์หน้า 20 ระบุในข้อ 5 ชัดเจนว่า "การสังเกต (Observation) ... วิธีการนี้มีค่าใช้จ่ายสูงมากกว่าวิธีการอื่น" เนื่องจากต้องส่งวิศวกรไปฝังตัวนั่งสังเกตหน้างานจริงเป็นเวลานาน
[ข้อสอบ 5 - วิเคราะห์ Scenario] ในการตรวจทานข้อกำหนดความต้องการ (Validation) หากพบว่าในเอกสาร SRS ระบุข้อกำหนดว่า "ระบบต้องทำงานได้อย่างรวดเร็วและไม่หน่วง" ข้อกำหนดนี้สอบตกเกณฑ์ข้อใด และควรปรับแก้อย่างไร?
▶
แนวคำตอบ:
1. เกณฑ์ที่สอบตก: สอบตกเกณฑ์ Clarity (ความชัดเจน) และ Verifiability (สามารถพิสูจน์ได้) ตามสไลด์หน้า 42 เพราะคำว่า "รวดเร็วและไม่หน่วง" มีความกำกวม และไม่มีหน่วยวัดเชิงตัวเลข ทำให้ไม่สามารถสร้าง Test Case เพื่อพิสูจน์แบบ Pass/Fail ได้

2. แนวทางปรับแก้: ต้องระบุเป็นตัวเลขเชิงปริมาณ เช่น "ระบบจะต้องตอบสนองต่อคำสั่งค้นหาข้อมูลและแสดงผลบนหน้าจอภายในเวลาไม่เกิน 1.5 วินาที เมื่อมีผู้ใช้งานพร้อมกันไม่เกิน 1,000 คน"
